# 02 · 写入协议：什么该记，记到哪，记成什么样

记忆系统的成败 90% 取决于**写入时的判断**。读错了可以再读，写错了会污染未来所有会话。

## 三步判断

对话中出现一条信息时，按顺序问三个问题：

### Q1：三个月后它还有用吗？

- **没用** → 不写。任务进度、临时状态、"现在正在做X"、一次性报错，全部靠 L3 会话归档回放，不占 L1。
  > 反例：`正在修复 index.md 的链接问题` —— 一天后就过期了，写进去只会让未来的会话困惑。
- **有用** → 进 Q2。

### Q2：它会变吗？（易腐性判定）

| 类型 | 例子 | 处理 |
|---|---|---|
| **稳定** | 硬件型号、用户偏好、目录结构、架构决策 | 写进 L1，长期有效 |
| **慢变** | 项目阶段、团队分工、技术选型 | 写进 L1，标注 `verified: YYYY-MM-DD` |
| **快腐** | 端口号、密码、token、版本号、临时路径、接口地址 | **不写值，只写"去哪查 + 怎么验"** |

**易腐值的正确写法**：

```markdown
## FreeLLMAPI
- 服务定义：~/projects/freellmapi（pm2 管理）
- 端口：见 `server/.env` 的 PORT，实测 `curl -s localhost:3001/v1/models | head -c 100`
- 状态以实测为准，不以文档为准

*verified: 2026-10-16*
```

**错误写法**（三个月后必然误导下一个会话）：

```markdown
## FreeLLMAPI
- 端口：3001
```

> 一个真实教训：同一条端口号在 4 个文件里出现过，其中 2 个是错的。只能靠"全文扫描 + 打一次真实请求实测"来确定当前值，而且**判定以实测为准，不以文档为准**。

### Q3：分到哪一类？

| 内容性质 | 目录 | 文件名 |
|---|---|---|
| 用户是谁、习惯、偏好、背景 | `memory/user-profiles/` | `用户名.md` |
| 配置、事实、踩过的坑、验证过的结论 | `memory/facts/` | `主题.md` |
| 可复用的操作步骤、排查流程 | `memory/procedures/` | `动作名.md` |
| 一次重要对话的决策过程 | `memory/session-notes/` | `YYYY-MM-DD-主题.md` |
| 项目当前进展、中断点 | `memory/context-snapshots/` | `项目名-state.md` |
| 原始日志、报告、废弃方案 | `archive/` | 按年月归档 |

**一个信息只写一处**。写在 `facts/` 就别在 `procedures/` 复制一份，用 wikilink 引用：`见 [[freellmapi配置]]`。

## 文件格式

**所有 L1 文件必须有 YAML frontmatter**，这是可维护性的前提。

```markdown
---
tags:
  - config
  - fact
date: 2026-10-16
verified: 2026-10-16
source: 实测
---

# 标题（一句话说清这是什么）

## 正文

...

## 相关文件

- [[另一个文件]]
- `memory/facts/xxx.md`

---

*创建: 2026-10-16 · 最后更新: 2026-10-16*
```

### frontmatter 的硬规则

**标签格式只有一种对的写法**：

```yaml
# ✅ 正确：单个 tags 键 + YAML 块数组
tags:
  - config
  - fact
```

```yaml
# ❌ 重复 tags 键
tags: '["config"]'
tags:
  - fact

# ❌ 标签里混进键值对（会导致 Obsidian 标红）
tags:
  - archive
  - referencesource_url: 某新闻站
```

**标签规范**：全小写英文，无空格，无 `#` 前缀。分类用固定词表，不要自由发挥：

| 标签 | 含义 |
|---|---|
| `user` | 用户相关 |
| `profile` | 完整画像 |
| `config` | 配置、环境 |
| `fact` | 已验证的事实 |
| `workflow` | 流程步骤 |
| `procedure` | 可复用的操作步骤 |
| `project` | 项目相关 |
| `decision` | 有理由的决策 |
| `pitfall` | 踩过的坑 |
| `reference` | 参考资料 |
| `system` | 记忆系统自身文件 |
| `archive` | 已归档 |

## 应该写 vs 不应该写

### ✅ 立刻写

- **用户明确纠正过一次的偏好** — `不要用中文列选项让我选，直接推荐一个`。这条价值极高，因为它一定会再发生。
- **会导致实际损失的环境事实** — `msys 的 rm 不进回收站`。写一次，永久免疫。
- **踩过并解决的坑 + 解法** — 尤其是"看起来像 A 问题，实际是 B"的那种。
- **决策和理由** — `选 MySQL 而不是 PostgreSQL，因为部署简便是首要考量`。理由比结论值钱。
- **跨会话的入口** — 项目在哪、账号在哪、详细配置在哪。

### ❌ 不要写

- **可以重新推导的** — 文件的完整内容、git log、`ls` 就能看到的东西。
- **任务进度** — `已完成第 3 步`。用 L3 会话记录。
- **一次性的猜测** — `可能是网络问题`。未验证的假设写进去就是污染。
- **大段原文** — 粘贴整篇文档。存原文放 `archive/`，L1 只写结论和引用。
- **密码和 token** — 任何情况下都只写"存在哪"，不写值。

## 追加 vs 覆盖

| 场景 | 操作 |
|---|---|
| 补充新信息到已有主题 | **追加**（append），保留历史 |
| 更正错误的信息 | **直接改**，并更新 `verified` 日期。**不要**在旧值下面叠 `UPDATE: 其实是…`，下一个会话会搞不清哪个是真的 |
| 主题被更好的一篇取代 | 旧文件顶部加 `> ⚠️ 已被 [[新文件]] 取代（2026-10-16）` |
| 清理合并重复文件 | 合并冲突内容 → 写新文件 → 删旧的 → **全文搜索旧文件名并更新所有引用** |

## 会话收尾检查

一次有实质内容的对话结束后，花 10 秒过一遍：

- [ ] 有没有用户纠正我的地方？→ 写 `facts/` 或 `user-profiles/`
- [ ] 有没有解决一个不明显的坑？→ 写 `facts/`，打 `pitfall` 标签
- [ ] 有没有做出并说明理由的决策？→ 写 `facts/` 或 `session-notes/`，打 `decision`
- [ ] 有没有产生新的入口/路径/账号？→ 更新 L0 指针 + `facts/`
- [ ] 有没有东西已经过时？→ 更新 `verified` 日期或标注取代

不用每次都写。没有值得记的就什么都别写 —— **记忆里的噪音比缺失更有害**，因为噪音会被当成事实执行。
