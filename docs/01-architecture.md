# 01 · 架构：为什么要分层

## 一个反例

大多数智能体的记忆是这么长出来的：

```
第 1 周：把用户名字、喜好写进系统提示。
第 4 周：把项目路径、API 端口、常用命令也写进去。
第 8 周：系统提示变成 8000 字符，每次请求都付这个钱，模型开始忽略中间部分。
第 12 周：满了。开始删。删错了，把「不要动生产库」删了。
第 16 周：接了个云端记忆服务，好用。第 20 周 402，记忆清空。
```

问题不是"记得太少"，是**没有分层，所有东西挤在同一个预算里**。

## 分层要解决的问题

| 问题 | 单层方案的后果 | 分层后 |
|---|---|---|
| 什么必须每次都知道？ | 分不清，只好都塞进去 | L0 只放"不知道就会做错事"的 |
| 详细配置放哪？ | 挤占预算，然后被压掉 | L1 文件，按需读 |
| 记不清文件叫什么？ | 找不到，等于没记 | L2 向量召回 |
| 三个月前的对话？ | 早就没了 | L3 归档 |
| 换工具怎么办？ | 记忆粘在旧工具里 | 文件跟着走 |

## 四层的职责边界

### L0 · KERNEL 内核记忆

**注入方式**：每次会话无条件注入，排在上下文最前面。
**硬预算**：2200 字符（这是 Hermes 系内置记忆的默认上限，其他工具按自己能力调，但**必须有硬上限**）。
**内容只有四类**：

```markdown
# 身份锚点（用户是谁 / 什么语言 / 什么交互风格）
用户：中文，专科大二，找 AI 应用实习。沟通极简，期望直接行动不要多问。

# 硬性约束（违反会造成实际损失）
msys/git-bash 的 rm 直接永久删除，不进回收站。执行前必须确认路径。
model 段配置只能 `hermes config set`，patch/write_file 会被静默拒绝。

# 环境关键路径（不记住就找不到东西）
知识库：D:\Obsidian Vault\
详细配置：memory/facts/system-config.md
GitHub 账号：memory/facts/github-account.md

# 指针（一行一个，格式固定）
```

**内核里绝对不能有的东西**：具体端口号、密码、API key、版本号、操作步骤、历史记录、任务进度。
它们全是**易腐值**或者**低复用内容**。

### L1 · VAULT 结构化知识库

**注入方式**：不注入。智能体通过 L0 的指针或检索，用文件读取工具按路径打开。
**组织方式**：按**用途**分目录，不按时间、不按字母。

```
memory/
├── user-profiles/   完整画像（L0 只有最小集）
├── facts/           事实、配置、踩坑记录 —— 会被反复引用
├── procedures/      可复用流程 —— 下次照着做
├── session-notes/   会话摘要 —— 有上下文的决策记录
└── context-snapshots/ 项目当前状态 —— 中断后恢复用
```

**为什么按用途分**：智能体找东西的思维是"我要做什么"，不是"那是几月写的"。按用途分，路径本身就成为线索：
`memory/procedures/部署静态站.md` 比 `memory/2026-07-14.md` 好找一百倍。

### L2 · INDEX 语义索引

**注入方式**：按查询召回，返回路径 + 摘要，不返回全文。
**实现**：任何本地方案都行 —— [qmd](https://github.com/tobi/qmd)（推荐，纯本地、BM25+向量混合）、Obsidian Smart Connections、Chroma、sqlite-vec。

**什么时候用**：
- ✅ 记得内容但记不住文件名（"上次那个关于相变片温度的结论"）
- ✅ 跨多个文件的主题汇总
- ❌ 已知确切路径（直接读文件，别浪费一次向量查询）

**必须验证索引不是空的**。这是最容易假成功的环节：

```bash
# 抽查一个真实文件的向量维度，nomic-embed-text 应该是 768
grep -o '"vec":\[[^]]*\]' .smart-env/multi/<file>.ajson | tail -1 | tr ',' '\n' | wc -l
# 输出 768 = 正常；输出 0 或 "vec":[] = 嵌入根本没跑起来
```

### L3 · ARCHIVE 原始会话归档

**注入方式**：从不主动注入。只在用户明确问"我们以前是不是聊过 X"时，用会话搜索回溯。
**内容**：完整对话日志、cron 执行报告、旧版快照、废弃方案。
**规则**：只增不改。要修正就往 L1 写新的，旧的说"已被 X 取代"。

## 数据流

```
                     ┌──────────── 写 ────────────┐
                     │                            │
对话 ──► 价值判断 ──► 分类 ──► L1 文件 ──► 索引更新 ──► L2
  │                    │
  │                    └──► 极少数高价值 ──► L0 一行
  │
  └──► 原始日志 ──► L3

                     ┌──────────── 读 ────────────┐
新会话 ──► 注入 L0 ──► 识别指针 ──► 读 L1 路径
                            │
                            └──► 指针失效/记不清 ──► L2 召回 ──► 读 L1
```

写入是**主动的**（智能体判断后落盘），读取是**被动的**（先 L0，再按需）。

## 设计取舍

**为什么不用数据库？**
因为记忆的主要消费者是语言模型和人，两者都最擅长读 Markdown。文本文件还能 git diff、能被 Obsidian 打开、能在手机上看、坏了用记事本救得回来。

**为什么 L0 必须硬上限？**
上限不是为了省钱，是为了**强制取舍**。没有上限，L0 会无限膨胀直到模型开始忽略它中间的内容（lost in the middle），那时候"注入"只是自欺欺人。有了上限，每次写入都要问一句"这不比里面现有的一条更重要吗"。

**为什么不用纯向量检索？**
因为关键信息（安全约束、禁止事项）**不能被"相似度不够"筛掉**。安全红线必须 100% 在场，这是 L0 存在的全部理由。
